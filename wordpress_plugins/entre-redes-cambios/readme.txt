Jornada calendar, plazo deadlines, and estado lifecycle for the Entre Redes player-change feature.

== Description ==

The Cambios plugin models the calendar of jornadas (matchdays) for a season — which does not exist as a first-class concept in SportsPress — along with the four operational deadlines (plazos) and the estado lifecycle (programada/jugada/dirimida/suspendida) each jornada goes through.

**Requires**: the Entre Redes base plugin must be installed and active.

== Installation ==

1. Install and activate the Entre Redes base plugin.
2. Upload `entre-redes-cambios/` to the `wp-content/plugins/` directory.
3. Run `composer install --no-dev` inside the plugin directory. This plugin ships one runtime dependency, `firebase/php-jwt`, used to verify the JWTs entre-redes-prode issues.
4. Activate the plugin from the WordPress admin Plugins screen.
5. Verify: `cambios_fecha`, `cambios_fecha_partido` and `cambios_settings` tables exist, and `cambios_settings` is seeded with default values.
6. To build a deployable zip instead of a local checkout, use `wordpress_plugins/build-plugin.sh entre-redes-cambios` from the repo — see the plugin's README.md.

= 0.1.34 =
* Schema: `cambios_solicitud.creada_por_wp_user` (nullable) records which WP user loaded a request on a captain's behalf. NULL means the captain filed it himself through the app — true for every existing row, so there is nothing to backfill. `solicitada_por` stays the captain's PLAYER id in both cases: the request is the captain's, the new column only says who typed it in. The column is added by `dbDelta()` on the first request after the upload (the version bump triggers it).
* The `solicitud.creada` event carries the WP user's id and display name (snapshotted) when a request was loaded from the admin; an app-filed request logs exactly what it always did.
* The comisión's new-request mail says "Cargada desde el panel por X" for such a request. The captain's receipt is unchanged — it is the confirmation that the request was loaded.

= 0.1.33 =
* Feature: cancelling a request confirms it to the captain by mail — "Cambios: Cancelamos tu pedido por X" — and says the half that actually matters: the plaza is free again, which is the whole reason he cancelled. Same switch as the other captain mails.
* It is its OWN method (`notificarCancelada()`), not an `anulada` branch of `notificarDecision()`, which still ignores that estado. A request reaches `anulada` by two different roads — the captain withdrawing it, and the comisión annulling an approved one from the tray — and they need opposite words. Routing both through one estado would tell a captain "cancelaste tu pedido" about something the comisión did to him.

= 0.1.32 =
* Feature: a captain can withdraw his own still-undecided request — `POST /cambios/solicitudes/{id}/cancelar`, and a "Cancelar pedido" button on Mis pedidos, shown only while the request is `pendiente`. Since 0.1.21 an open request LOCKS its plaza and its incoming player, so a captain who picked the wrong name was stuck: he could not file the right one until somebody else resolved the wrong one, and his only way out was to write to the comisión — the back-and-forth outside the system that this whole feature replaced. With a window that closes on a Thursday night, a typo could cost him the fecha.
* An `aprobada` is NOT cancellable by the captain (409 `solicitud_ya_resuelta`). The comisión already acted on it, undoing their decision is theirs to do — the tray has its own button — and a captain cancelling an approval would silently change what Friday's lote contains.
* Ownership is checked against the AUTHORISED season/team, never against what the body claims, and a solicitud belonging to another team answers EXACTLY like one that does not exist (404 `solicitud_no_encontrada`): telling them apart would make the endpoint a probe for other teams' request ids.
* The audit trail names the captain with a "Capitán " prefix (`cambios_decision.decidida_por_nombre`), so nobody reading the histórico later mistakes a withdrawal for a decision the comisión took. `resuelta_por` holds the captain's PLAYER id here, unlike every other writer of that column — it is write-only audit that nothing reads for logic, and the name is what a human actually reads.

= 0.1.31 =
* Feature: the CAPTAIN is emailed about his own request — a receipt when he files it, and the decision when the comisión approves or rejects it. Its own switch on the Configuración screen, separate from the comisión's: one may be wanted without the other. There is no address to configure; it is resolved per captain from the Google or Apple account they sign in with (`Notificaciones\CapitanEmailResolver`: `solicitada_por` -> `prode_associations.player_id` -> `prode_users.email`). Deleted associations and deleted users are excluded — an account somebody removed is not a way to reach them — and when a player holds more than one, the most recently used login wins, because that is the inbox they are actually reading. No address means no mail, logged, never a guess.
* The approval mail says, in bold, that it is NOT final: the change takes effect when the lote is published, and until then the player cannot play. That is the single most likely harm this feature can cause — a captain who reads "aprobado" on Wednesday and fields the player on Saturday has broken the rule believing he followed it.
* Neither the dictamen nor its motivos reach the captain. Chances of approval are the comisión's to discuss, and printing the ruleset's automatic objections beside a human rejection tells him a reason that was not the real one. The only explanation he gets is the note a human wrote, and when there is none the mail says so rather than inventing one. The "Gestionar" button is absent too: it points at wp-admin, where a captain cannot go — he is sent to Mis pedidos in the app.
* `notificarDecision()` ignores any estado it has no copy written for (`publicada`, `anulada`) instead of improvising one. Without that guard they fall through to a missing template and are swallowed by the catch: the same silence, but every one logged as a failure, which over a Friday lote would be a stream of fake errors in the one durable slot this host has for real ones.

= 0.1.23 =
* Feature: `Admin\ConfiguracionPage` — a third screen under "Cambios" (slug `cambios-configuracion`, same `gestionar_cambios` capability) that makes the policy rows of `cambios_settings` editable without a database client. The four plazo offsets (apertura de solicitudes, cierre de regresos, cierre de cambios, publicación), the exención del arco and the prioridad de padres. ZERO behaviour change: every row it writes was already read by `Calendario\Settings` and already honoured by the ruleset — until now the only way to change one was a hand-written UPDATE.
* Reliability: `Calendario\PlazosValidator` refuses a plazo set whose offsets are out of chronological order. `PlazosCalculator::isWithinSolicitudWindow()` is `now >= apertura && now <= cierre`, and nothing checked that the first was earlier than the second — swapping two numbers produced a window that NEVER opens, with no exception, no event and no message, indistinguishable from "the feature is broken". It also refuses non-integer days, days outside -90..0, a malformed `HH:MM:SS`, and a well-formed but impossible time such as `25:00:00` (which `DateTimeImmutable` would silently roll into the next day). Every problem in the set is reported at once, and a refused save writes NOTHING — not even the rows that were individually fine, because a half-applied calendar is worse than the old one when the operator believes they changed it.
* Feature: a captain-facing kill switch (`cambios_habilitados`, ON by default, plus `mensaje_deshabilitado`). Turned off, every `/cambios/` REST route answers HTTP 503 `cambios_deshabilitado` with the sentence the comisión wrote, and the app shows it instead of the roster — no retry button, because nothing went wrong and retrying cannot help. `Plugin::gateCambiosWhenDisabled()` runs on `rest_pre_dispatch`, so not one route callback runs while the switch is off: a per-controller check is something a future route can forget, and a kill switch is only worth having if it has no gaps. 503 and not 403 on purpose — a temporary closure is not a permission problem, and the app needs to tell "contactate con la comisión" from "you are not a captain". The bandeja and the histórico do NOT go through REST and keep working, so the comisión can stop the inbox and still process what is already in it. Saving refuses to close the feature with an empty message; the text is sanitized and capped at 300 characters where it is saved, and it is the ONE server string the app renders verbatim — opted into by code for that single error code, never by default.
* Feature: the liberation minimum is configurable (`minimo_fechas_cambio`, default 3, clamped 1..10 — a `0` would void the rule and let a substitute be returned the same fecha they arrived). The reglamento's "3 fechas" is a rule the comisión can change, not a constant of the domain. It is read ONCE where the object graph is built and threaded in, because neither the rules nor `Dictamen\DictamenEngineFactory` can reach the database; the number now has exactly one source instead of two. The second one was easy to miss: `Dictamen\BloqueoReemplazoEvaluator` kept its own `TOPE_FECHAS = 3` for the `topeTresFechas` branch of `BloqueoReemplazoPolicy`, so a reglamento change would have moved the liberation minimum and left the ex-reemplazo block capped at 3, the two branches then disagreeing about how long a player is held.
* Note on semantics: the minimum is NOT frozen per ocupación — `Plazas\CadenaResolver` derives everything from scratch on every call, so raising it re-blocks substitutes that were already liberable and lowering it releases several at once. That is the intended reading of a reglamento change (it applies to everyone) and it is why the field's own help text says to touch it between fechas, not on a Thursday.
* Internal: `Calendario\SettingsWriter`, the one writer of `cambios_settings`, kept separate from `Settings` so that class stays the pure reader its docblock promises (its value is a per-setting audit of which direction is safe when a read FAILS). Every write records `settings.modificado` with the old and new value; a row whose value did not change is skipped, so the audit trail means "somebody changed this" rather than "somebody pressed Guardar". A failed write records `settings.escritura_fallida`. The upsert is UPDATE-or-INSERT rather than `ON DUPLICATE KEY UPDATE`: the SQLite test shim does not rewrite that MySQL-only syntax, so every test would have exercised the failure branch while production exercised the happy one.

Every new read fails closed (logged `lectura.fallida` and thrown, never read as "nothing to see"), and the page uses batched reads, never one query per row.

= 0.1.21 =
* Feature: two new dictamen rules (the eleventh and twelfth), and creation is REFUSED for them: `POST /cambios/solicitudes` answers HTTP 409 (`code` = `plaza_con_solicitud_abierta` or `entrante_con_solicitud_abierta`, no detail about another team's request) and persists nothing — for the grouped `reasignacion_arquero` on either leg too (`SolicitudRepository` throws `SolicitudAbiertaException` between the evaluation, which already ran before any write, and the first insert). Only these two codes refuse; a request that breaks any of the other ten rules is still stored `pendiente` with its motivos, because those are the process owner's to overrule. The reason: `publicarLote()` aborts the whole lote when one row's fresh dictamen does not `procede`, so a stored duplicate would stop every team's change from publishing, and as an open request it would also hold the plaza and player it names. `Dictamen\Reglas\PlazaSinSolicitudAbierta` (`plaza_con_solicitud_abierta`) refuses a request against a plaza that already has an open one; `Dictamen\Reglas\EntranteSinSolicitudAbierta` (`entrante_con_solicitud_abierta`) refuses naming a player who is already the incoming player of an open request, anywhere in the season and across every team. "Open" is `pendiente` OR `aprobada` (`EstadoSolicitud::abiertas()`) — an approved request still holds its plaza and player until Friday's lote. A grouped `reasignacion_arquero` is covered on both movements: each leg is evaluated in its own context, and the lookups match both plaza columns (`plaza_id`, `plaza_campo_id`) and both entrante columns (`entrante_player_id`, `entrante_campo_player_id`). `regreso` has no entrante, so the player rule stays silent for it.
* Fix (needed by the above): `SolicitudRepository::publicarLote()` re-evaluates every approved request, and an approved request is itself open — it would have been rejected by its own row. `SolicitudDeCambio::conSolicitudId()` now tags the rebuilt request with its row id and `DictamenContextAssembler` excludes that row from both lookups.
* Feature: `GET /cambios/plazas` returns `solicitud_abierta` per plaza — `null`, or `{ id, estado }` — so the app can hide "Pedir cambio" and show a legend instead. Resolved for the whole team in ONE query (`SolicitudesAbiertasReader::abiertaPorPlazaDeEquipo()`), never one per plaza; a grouped request marks both of its plazas.
* Feature: `CandidatosResolver::buscarPaginado()` excludes every player already named by an open request from the POPULATION, before `total` is counted and before the page is sliced (the same "filter first, count second, slice third" ordering as the ceiling filter, so a page can never be emptied after the fact).
* Reliability: every new read (`Solicitudes\SolicitudesAbiertasReader`) fails closed — a failed query is logged as `lectura.fallida` and thrown, never read as "nothing is open". `listar()` wired without a reader answers a logged 500 rather than `solicitud_abierta: null` for every plaza.
* Fix: `POST /cambios/solicitudes` now checks that `plaza_id` belongs to the authorised `team_id`/`season_id` before anything else (400 `plaza_no_encontrada`, for every tipo). Before, a captain could name another team's plaza, use the 409 as an oracle on its open requests, and store a row that locked its real owner out.
* Fix: the check-then-insert race. Creation (dictamen evaluation + insert) now runs inside ONE per-season critical section (`Solicitudes\Lock\CreationLock`, production `MysqlCreationLock` over `GET_LOCK`, 5 s bounded wait, released on success, refusal and exception). If the lock cannot be taken the answer is a retryable 503 `creacion_ocupada` ("Probá de nuevo en unos minutos"), never a 409, and nothing is evaluated or stored. A controller wired without a lock refuses to create.
* Feature: `Admin\BandejaPage` can now ANULAR an `aprobada` row (separate form per row, outside the publish-lote form, explicit server-checked confirmation, same authorization and the usual `cambios_decision` row) — the way out when a stuck approved row would abort the whole Friday lote.
* Fix: a lote abort caused by an open-request motivo now names the conflicting row (`... (en conflicto con la solicitud #N)`); `EntranteSinSolicitudAbierta` carries `solicitud_id` in its motivo `datos` (never in its message, and never shown to a captain: such a request is refused before it exists).
* Fix: observability. `solicitud.lote_abortado` is now `solicitud.lote_publicacion_fallida`, so `Observability\WpEventLog` — which persists only `fallid` events, and this host has no PHP log — keeps an aborted Friday lote in `entre_redes_cambios_ultimo_error`. The routine duplicate refusal is `solicitud.creacion_rechazada_duplicado` (season, team, plaza(s), tipo, requester, code) and is deliberately NOT persisted: a refused duplicate is the system working, and persisting it would overwrite that single slot and bury a real failure such as the lote abort.
* Fix: a `regreso` now COMMITS its returning titular. The titular of an open `regreso`'s plaza counts as an incoming player (derived by joining `cambios_plaza`, in the same single query): he is hidden from candidate lists and refused as the entrante of any other open request. The `regreso` never blocks itself. The mirror is closed too: a `regreso` is refused (`entrante_con_solicitud_abierta`) when its returning titular is already the incoming player of ANOTHER open request.
* Note: requests that were already open on the same plaza or player BEFORE this release are not migrated; if two such approved rows exist, publishing the lote that contains them aborts with the new motivo until one is annulled.

= 0.1.20 =
* Fix: every `/entre-redes/v1/cambios/` REST response now carries `Cache-Control: no-store, no-cache, must-revalidate, max-age=0, private`, `Pragma: no-cache` and `Vary: Authorization` (`Plugin::denyCambiosResponseCaching()`, on `rest_post_dispatch`). = 0.1.15 =
* Add: `Dictamen\SolicitudDeCambio::TIPO_REASIGNACION_ARQUERO` and `cambios_solicitud` support for GROUPED goalkeeper reassignments — one request carrying two movements (the goal plaza's occupant becomes a field titular; an outside player fills the field plaza that titular leaves behind), approved/rejected/published as a single unit, per the process owner's explicit request ("deberíamos hacer que el pedido se agrupe uno solo y que la aprobación sea en grupo"). Slice 2 of "la exención del arco" (slice 1, 0.1.13, added the stored `cambios_plaza.es_arco` fact this slice reads).
* Add: `DictamenContext::exencionArco()` — a per-evaluation context flag, `false` everywhere except movement 1 of a grouped reassignment. Exactly two of the ten existing rules read it: `Reglas\PuntajeDentroDelTecho` skips the goal plaza's techo entirely for that leg, and `Reglas\EntranteDisponible` does not treat the titular's own, still-open field-plaza occupation as a conflict for that leg. Every other rule, and movement 2 (the vacated field plaza), is unchanged — judged by the ordinary ten-rule ruleset with no exemption at all.
* Add: `Dictamen\DictamenPipeline::evaluateGrupo()` — assembles two ordinary `DictamenContext`s (one per movement) and unions their motivos into one `Dictamen`, rather than teaching the ruleset about pairs.
* Add: `Calendario\Settings::exencionArcoActiva()` (`cambios_settings` key `exencion_arco_activa`, default ON) — a real, persisted switch for the whole exemption. When off, movement 1 is judged exactly like an ordinary `sustitucion` (no techo skip, no occupied-plaza exemption), which in practice refuses every grouped request, since its entrante structurally always already occupies the field plaza he is meant to vacate.
* Add: `Solicitudes\SolicitudRepository::crearReasignacionArquero()` and `cambios_solicitud` columns `plaza_campo_id` / `entrante_campo_player_id` / `ocupacion_campo_id` — the vacated field plaza and its new occupant are snapshotted at request time, same "saliente_player_id lesson" (0.1.11) as every other write-time fact this table freezes rather than re-derives later. No backfill needed (the table was confirmed empty in production) and no SportsPress taxonomy dependency, unlike `es_arco`'s 0.1.13 backfill.
* Change: `Solicitudes\SolicitudRepository::publicarLote()` now applies a grouped reassignment's two movements inside its one atomic transaction, in a fixed order (the vacated field plaza first, the goal plaza second) that guarantees the titular never occupies two plazas at once, not even momentarily uncommitted. The fresh re-evaluation `publicarLote()` already ran for every ordinary solicitud now re-runs BOTH movements for a grouped one, via `evaluateGrupo()`, so a grouped request that no longer holds still aborts the whole lote.
* Change: `Admin\BandejaPage` now renders both movements of a grouped request ("Arco — Sale/Entra" and "Campo — Sale/Entra") so the process owner can judge the whole move, not half of it.

= 0.1.14 =
* Fix: a production incident left all 30 teams' `cambios_plaza.es_arco` at `0` after the 0.1.13 upgrade. Root cause: `Migrations\MigrationRunner::runIfOutdated()` ran from `Plugin::boot()` on `plugins_loaded` — BEFORE SportsPress registers its `sp_position` taxonomy on `init` (priority 10) — so `wp_get_object_terms()` returned a `WP_Error` for every call the `es_arco` backfill made, and `Plazas\PosicionResolver::resolverParaIds()` silently read that as "nobody has a position". `Plugin::boot()` now defers the migration call to an `init`-priority-11 callback (strictly after SportsPress's own priority 10), so the taxonomy always exists by the time it runs.
* Fix: `Plazas\PosicionResolver::resolverParaIds()` now throws a `\RuntimeException` (recording `posicion.resolucion_fallida`) instead of silently treating a failed `wp_get_object_terms()` call (a `WP_Error`, or anything else not an array) as "nobody has a position" — the root cause of the incident above. Every caller (`Plazas\PlazaRepository::doOpenPlaza()`, `Plazas\Alta\TitularesListImporter::planificar()`, `Dictamen\DictamenContextAssembler`, `Plazas\CandidatosResolver::buscarPaginado()`) now lets this propagate rather than degrading — a failed read must never become a silent permission (e.g. a goalkeeper candidate quietly admitted into a field plaza's list).
* Fix: `Migrations\MigrationRunner::backfillEsArco()` now refuses to write `es_arco = 0` as a guess when position resolution fails — it writes NOTHING and returns `false`, and `run()` leaves `cambios_db_version` un-bumped so the backfill retries (and, once the hook-ordering fix above lands, succeeds) on the very next request, instead of recording a half-done upgrade as complete.
* Fix: `Migrations\MigrationRunner::checkEsArcoInvariant()`'s own `admin_notice` only ever rendered if the ONE request that happened to run a version-upgrade migration was ALSO an admin page load — confirmed in production: all 30 teams sat at `es_arco=0` with no notice ever shown. The check now PERSISTS its verdict (`entre_redes_cambios_arco_invariante_violaciones`, cleared automatically once repaired), and a new `renderEsArcoInvariantNotice()` renders it from a callback `Plugin::boot()` wires unconditionally on every admin request — an operator now sees the notice on their next wp-admin visit, not only in that one arbitrary request. Renamed the recorded event from `arco.invariante_violada` to `arco.invariante_fallida` so it also lands in `entre_redes_cambios_ultimo_error` (readable via phpMyAdmin with no admin UI needed), matching `WpEventLog`'s `fallid`-substring convention. `checkStorageEngine()` has the identical one-shot-notice shape and is NOT changed by this release — a narrower, pre-existing gap left as a documented follow-up.

= 0.1.12 =
* Add: a new dictamen rule, `Dictamen\Reglas\ArqueroNoOcupaPlazaDeCampo` (motivo `arquero_no_ocupa_plaza_de_campo`) — a goalkeeper may not take over a plaza that is not the goalkeeper's plaza. "Goalkeeper" (the CANDIDATE definition) means `sp_position` term 3 ("Arquero") OR term 125 ("Arquero Sup." — the process owner confirmed explicitly that a backup goalkeeper counts); "the goalkeeper's plaza" (the PLAZA definition) means the plaza's TITULAR position is term 3 ONLY — there are exactly 30 of those per season, one per team, which is what keeps "the goal" an identifiable, singular plaza. The two definitions are deliberately disjoint and are never unified. The rule is asymmetric on purpose: it only blocks goalkeeper → field plaza, never field player → goalkeeper's plaza (the pending "exención del arco" direction stays legitimate). Registered in `DictamenEngineFactory::reglas()` (now ten rules) — `Solicitudes\SolicitudRepository::publicarLote()` re-runs the full dictamen before applying, so a hand-crafted or stale-client request is still refused here regardless of what the candidate list showed.
* Change: `Plazas\CandidatosResolver::buscarPaginado()` now also excludes a goalkeeper from a FIELD plaza's candidate population — a convenience mirroring the dictamen rule above (never a substitute for it), applied in the same place and for the same reason as the existing unrated/over-ceiling population filters: after the population's metrics are in hand, before `total` is computed, before `array_slice()` takes a page. The position lookup for the whole population (plus the plaza's own titular) runs in exactly ONE batched `Plazas\PosicionResolver::resolverParaIds()` call, never one per candidate.
* Add (app): "Mis Solicitudes" now renders a plain-Spanish message for `arquero_no_ocupa_plaza_de_campo` via `cambiosMotivoMensaje()` instead of a raw code.

= 0.1.11 =
* Add: `cambios_solicitud` gains `saliente_player_id`, captured once at `Solicitudes\SolicitudRepository::crear()` time from the plaza's vigent ocupación — never re-derived later, so an old solicitud keeps naming who actually left even after the plaza's chain has since advanced. `GET /cambios/solicitudes` now returns `sale`/`entra` objects (`{ player_id, nombre, puntaje }`) for every row: for a `sustitucion`, `sale` is this stored saliente and `entra` is the stored `entrante_player_id`; for a `regreso` (whose `entrante_player_id` is always NULL — who returns is never a choice the request makes), `entra` is instead the plaza's permanent `titular_player_id` and `sale` is the same stored saliente — the suplente the titular displaces. Names and puntajes for the whole page are resolved in one batched call each (`get_posts()`/`get_the_title()` cache priming, `Plazas\JugadorMetricasReader::resolveMuchos()`), never one query per row. An unresolvable puntaje stays `null` rather than a fabricated value; a `saliente_player_id` that predates this column (a row created before 0.1.11) degrades its whole `sale` side to `{ player_id: null, nombre: null, puntaje: null }` rather than guessing.
* Add (app): "Mis Solicitudes" now renders `Sale: <Apellido, Nombre> [<puntaje>]` and `Entra: <Apellido, Nombre> [<puntaje>]` under each pedido, using the app's existing `formatearPuntaje()` so a whole-number puntaje never renders with a spurious decimal. An unknown puntaje omits the brackets entirely rather than showing `[]` or `[-]`; an unrecorded side (predates the backend column) renders as "Sin registrar" instead of a blank line.

= 0.1.10 =
* Fix: `GET /cambios/plazas/candidatos` could return an EMPTY page while `X-WP-Total` reported a population in the hundreds — the exact production incident: opening "Padrón Completo" with no puntaje chip selected showed "No encontramos candidatos disponibles para esta plaza" on a plaza with a 4.5 techo, even though 81 published players were rated 4.5 and below. Root cause: `Plazas\CandidatosResolver::buscarPaginado()` sorts `puntaje DESC` (0.1.8), and the techo was only enforced AFTER a page was already sliced — so the 31 published players rated 5.0 alone filled page 1 at `per_page=20`, and the per-page filter then stripped every one of them, returning an empty page. The techo now excludes an over-ceiling candidate from the POPULATION itself, in the same place and for the same reason as the unrated-candidate exclusion added in 0.1.9 — before `X-WP-Total` is computed and before pagination. `?incluir_no_viables=1` can no longer surface a `motivo: 'puntaje_excede_techo'` row (there is nothing left in the population for it to surface) but still surfaces a page's own phase-2 rejections (`ocupa_otra_plaza_vigente`, `bloqueado_por_cierre_truncado`) unchanged. `total` is therefore very slightly optimistic — it counts the population before phase-2 verdicts — a materially smaller and more even-handed overcount than the one this removes, since phase-2 non-viables are a small minority scattered across the whole population rather than concentrated at the top of the sort.
* Fix (app): the Flutter app rendered the empty state the instant a page arrived with zero candidates, even when the server reported more pages remain (`hasMore: true`) — the app-side half of the same incident, since a page can still legitimately come back short or empty after the backend's own per-page phase-2 filter runs. `CambiosCandidatosController` now keeps fetching subsequent pages, without showing the empty state, until a page returns at least one candidate, the server reports no more pages, or a small cap on consecutive empty pages is reached (a defensive bound against a server that kept returning empty pages forever).

= 0.1.9 =
* Change: `GET /cambios/plazas/candidatos` now excludes a candidate with no resolvable puntaje from the population entirely, in BOTH screen sections ("Lista de Espera" and "Padrón Completo") as well as the default season-registered population — not just the whole padrón-wide population. Without a puntaje there is nothing to evaluate against the plaza's techo, so such a player is not a candidate at all (previously it was rendered as a non-viable row with `motivo: 'puntaje_indeterminado'`, buried last by the 0.1.8 sort). The exclusion happens in `Plazas\CandidatosResolver::buscarPaginado()`, before `X-WP-Total` is computed and before pagination, so it never produces a short page or an inflated total. `Plazas\CandidatosResolver::paraPlaza()` / `::paraSeccion()` (the padres-priority rule's own, unpaginated pool) are unchanged by this — an indeterminate puntaje was already never viable there. The dictamen engine's own refusal of an indeterminate entrante (`Dictamen\Reglas\PuntajeDentroDelTecho`) is unaffected; this is a presentation-layer exclusion, not the enforcement.
